CONCURRENT TASK DISPATCHER (RUST) - MARIO TREVINO

HOW TO BUILD AND RUN:

    ENSURE YOU HAVE RUST AND CARGO INSTALLED.
    FROM THE final_project DIRECTORY, USE THE FOLLOWING COMMANDS TO RUN DESIRED EXPERIMENTS:

    FOR EXPERIMENT A (BALANCED WORKLOAD), RUN:

    cargo run --bin experiment_a

    FOR EXPERIMENT B (STRESSED WORKLOAD), RUN:

    cargo run --bin experiment_b

SUMMARY OF DESIGN:

    ARCHITECHTURE: 
    THIS SYSTEM FOLLOWS A PRODUCER-CONSUMER PATTERN. THE PRODUCER (A SINGLE DISPATCHER THREAD) GENERATES TASKS, AND THEN PLACES THEM
    INTO A SHARED READY QUEUE. THERE IS A BOUNDED POOL OF 4 WORKER THREADS (THE CONSUMERS) WHICH PULL TASKS FROM THIS QUEUE AS THEY
    BECOME AVAILABLE.

    SYNCHRONIZATION: *CHANNELS: THERE IS AN MPSC CHANNEL TO IMPLEMENT THE TASK QUEUE, WHICH PROVIDES A THREAD-SAFE BRIDGE BETWEEN THE DISPATCHED
    AND THE WORKERS. 
    - Arc<Mutex<Receiver>> IS USED TO ALLOW MULTIPLE WORKERS TO SAFELY SHARE THE SINGLE RECEIVER END OF THE CHANNEL.
    - AtomicU32 and AtomicU64 IS USED FOR HIGH PERFORMANCE AND LOCK-FREE TRACKING OF SYSTEM METRICS ACROSS THREADS.

    SCHEDULING FORMAT: FIFO WAS IMPLEMENTED (FIRST IN, FIRST OUT) TO MINIMIZE SCHEDUULING OVERHEAD AND MAXIMAIZE MAKESPAN EFFICIENCY. THIS
    ENSURES THAT TASKS ARE HANDLED IN THE ORDER THEY ARRIVE WITHOUT CRAZY RE-PRIORITIZATION LOGIC THAT COULD SLOW DOWN RUNTIME.


SUMMARY OF EXPERIMENTS:

    EXPERIMENT A:
    SETUP - 500 MIXED CPU/IO TASKS. DURATIONS FROM 100MS TO 500MS.
    RESULT - AVERAGE WAIT TIME WAS 18488.20 ms.
    OBSERVATION - WORKLOAD WAS HANDLED SMOOTHLY. WORKERS WERE ABLE TO KEEP UP WITH THE ARRIVAL RATE. QUEUE LENGTH WAS MANAGEABLE.

    EXPERIMENT B:
    SETUP - 500 MIXED CPU/IO TASKS. DURATIONS FROM 1-3 SECONDS. ARRIVING IN ≈1MS INTERVALS.
    RESULT - AVERAGE WAIT TIME WAS 122845.41 ms.
    OBSERVATION - THIS EXPERIMENT STRESSED THE SCHEDULER. THE QUEUE WAS 'BACKED UP', SINCE ALL TASKS ARRIVED WAY FASTER
    THAN THE 4 WORKERS COULD EXECUTE THEM. THIS CAUSED THE WAIT TIMES TO INCREASE BY OVER 500%.


TOOL USE DISCLOUSURE:

    TOOLS USED: GEMINI AI

    HELP PROVIDED: IT HELPED ASSIST ME IN WEIGHING THE TRADE-OFFS BETWEEN USING A GLOBAL MUTEX VS USIGN A CHANNEL BASED QUEUE.
    IT ALSO HELPED ME WORK ON USING ATOMIC PRIMITIVES TO ENSURE THE METRICS DIDN'T INTERFERE WITH THE SYSTEMS
    TOTAL RUNTIME.

    EXAMPLE OF ADVICE ACCEPTED: I TOOK THE IDEA OF USIGN A "POISON PILL" PATTERN FOR IT'S SHUTDOWN. IT SUGGESTED I USED WRAPPED
    TASKS IN AN OPTION<T> AND SEND A NONE SIGNAL, WHICH ALLOWED FOR A CLEAN SHUTDOWN.

    EXAMPLE OF ADVICE FIXED: GEMINI SUGGESTED IMPLEMENTING A COMPLEX PRIORITY QUEUE TO HANDLE THE DIFFERENT KIND OF TASKS, BUT I REJECTED
    THAT SUGGESTION AND DECIDED TO GO FOR A MORE STRICT FIFO STRUCTURE, SINCE MAKESPAN WAS A PRIORITY. I BELIEVED HAVING A COMPLEX PRIO QUEUE
    WOULD MEAN THE WORKERS WOULD SPEND LESS TIME ACTUALLY WORKING THE TASKS AND SPEND MORE TIME WAITING ON DISPATCHED LOGIC.
